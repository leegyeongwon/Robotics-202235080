## 1. Embedded-Based Low-Level Control

### Robot System Architecture
Each function in a robot system requires a different control cycle, so roles are typically split into high-level and low-level layers:

* **High Level (SBC / ROS2):** Heavy computation, high memory usage — SLAM (environment perception), camera, LiDAR, path planning, navigation.
* **Low Level (MCU / RTOS):** Short, periodic real-time control execution — motor PWM, encoder data processing, PID control, GPIO, UART, and direct hardware control.

### MCU & Basic Electronics
* **MCU (Microcontroller Unit):** Integrates CPU, memory, and peripherals on a single chip (similar to an SoC, though SoCs typically run full OSes like Linux).
* **Ohm's Law:** $V = I \times R$
* **Floating & Pull Resistors:**
  * **Floating state:** Unconnected input pin causes unstable, jittering voltage when a button is pressed.
  * **Pull-down resistor:** Default state is LOW (`0V`); pressed state is HIGH.
  * **Pull-up resistor:** Default state is HIGH; pressed state is LOW.
* **Switch Bouncing:** Mechanical contacts vibrate briefly when pressed, causing rapid voltage fluctuations (requires hardware or software debouncing).
* **PWM (Pulse Width Modulation):** Controls average power delivered to actuators (like motors) by varying the duty cycle.

### Sensors
* **IMU (Inertial Measurement Unit):** Combines a gyroscope and an accelerometer (sometimes a magnetometer) to measure orientation and acceleration.
* **GNSS (Global Navigation Satellite System):** Satellite positioning system (e.g., GPS); cannot be used indoors.
* **Wheel Encoder:** Measures how much a wheel has rotated. Essential for odometry, though prone to drift/error when wheels slip.
* **LiDAR:** Measures 360-degree distances using laser pulses.

### Embedded Communication Protocols
Two ways to transfer data (e.g., `IMU --[inertia]--> MCU`):
1. **Synchronous:** Uses a shared clock signal generated by the MCU to synchronize data transfer frequency between devices.
2. **Asynchronous:** No shared clock. Data is sent at an agreed baud rate, stored in the MCU's buffer, and read when needed (requires buffer management).

#### UART (Universal Asynchronous Receiver/Transmitter)
* Asynchronous point-to-point serial communication (`TX` $\leftrightarrow$ `RX`), commonly used for debugging and sensors like 2D LiDAR.
* **Baud rate:** Data transmission speed in bits per second (`bit/s`), e.g., `Serial.begin(115200)`.
* **Frame format (LSB - Least Significant Bit sent first):**
  `(Start bit) + [8-bit Data Byte] + (Stop bit)`

#### I2C (Inter-Integrated Circuit)
* Synchronous communication using two shared lines: **SDA** (Serial Data) and **SCL** (Serial Clock). Multiple sensors can share the same two pins on the MCU.
* **Architecture:** Master (MCU) and Slaves (sensors). Each slave has a unique address.
* **Start Condition:** Communication begins when **SDA** transitions from HIGH to LOW while **SCL** remains HIGH.
* **Data Transfer & ACK/NACK:** While SCL is HIGH, SDA must remain stable so data bits can be read reliably. Slaves respond with **ACK** (Acknowledge) or **NACK** (Not Acknowledge) when addressed by the master.

## 2. ROS2 Basics (`ROS_DOMAIN_ID: 14`)

### Core Concepts
* **ROS2 (Robot Operating System 2):** Not a true OS, but a robotics middleware framework. Processes run in isolated memory spaces and communicate over a standardized protocol. Includes rich ecosystem tools like RViz and Gazebo.
* **Node:** A single executable process in ROS2 (roughly one process per function/terminal).
* **Topic:** Named bus for continuous, asynchronous data streaming using a **Publisher / Subscriber** model. Topics can be grouped with `/` (e.g., `/turtle1/cmd_vel`).
* **Message Type:** Defines the data structure of a topic (e.g., `int`, `float`, `geometry_msgs/msg/Pose`, which contains nested fields like `pose.position.x`).
* **Visualization:** Use `rqt_graph` to inspect active nodes and topic connections.

### DDS & QoS (Quality of Service)
ROS2 runs on **DDS (Data Distribution Service)**, allowing fine-tuned communication policies between nodes:
* **Reliability:**
  * *Best Effort:* Fast, prioritizes latest data, may drop packets (good for high-frequency sensor data).
  * *Reliable:* Guarantees delivery via retransmission (good for commands/states).
* **Durability:**
  * *Volatile:* Late-joining subscribers only receive new messages.
  * *Transient Local:* Late-joining subscribers receive previously published messages (latched behavior).

### `colcon` Workspace & Build System
* **Workspace Structure:**
  * `src/`: Source code of ROS2 packages written by developers.
  * `build/`: Intermediate files generated during compilation and building.
  * `install/`: Built executables, libraries, and environment setup files (`setup.bash`).
  * `log/`: Build and test logs.
* **`colcon`:** CLI build tool that scans the workspace, analyzes package dependencies, and builds selected packages.
* **Launch File:** Python script (`*.launch.py`) used to start and configure multiple nodes simultaneously with a single command.

### Communication Patterns & Custom Interfaces
* **Service (`.srv`):** Synchronous **Client–Server** pattern (`Request` $\rightarrow$ `Response`) for quick, one-time tasks (e.g., querying a sensor state).
* **Action (`.action`):** Asynchronous **Client–Server** pattern (`Goal` $\rightarrow$ continuous `Feedback` $\rightarrow$ final `Result`) for long-running tasks (e.g., navigating to a target coordinate).
* **Custom Interface:** User-defined `.msg`, `.srv`, or `.action` data structures.

### High-Level Architecture & AMR
* **AMR (Autonomous Mobile Robot):** Mobile robot capable of navigating environments independently.
* **Perception–Planning–Action (PPA) Loop:**
  * **Perception (Cognition):** Gather sensor data and estimate the robot's pose and surrounding environment.
  * **Planning:** Compute and dynamically update paths/trajectories.
  * **Action (Control):** Execute motion commands to follow the planned path.

### Odometry, Quaternions & TF (Transforms)
* **`/odom`:** Topic publishing odometry data (estimated distance traveled and rotation).
* **Quaternion:** 4D orientation representation (w, x, y, z) that avoids gimbal lock, constrained by w^2 + x^2 + y^2 + z^2 = 1.
* **TF2 (Transform Library):** Tracks coordinate frame relationships over time (`Parent Frame` $\leftrightarrow$ `Child Frame`).
  * **Static TF:** Fixed spatial relationship between frames (e.g., base link to LiDAR); low network overhead.
  * **Dynamic TF:** Continuously changing spatial relationship (e.g., `odom` to `base_link`); requires frequent updates.
  * **Broadcaster:** Publishes relative transforms between frames in real time (manages static and dynamic transforms separately).
  * **Listener:** Subscribes to transform topics and computes coordinate transformations between any two frames.
